# Local Mock + mitmproxy

A local replay environment for browser-agent experiments. The manager runs at `http://mock.test/`, while registered mock sites use their original domains and paths inside a dedicated proxy browser. Requests handled by the proxy never reach the original servers.

## Windows quick start

Requires Python 3.12 or later and Google Chrome.

1. Clone this repository or extract its ZIP into a new folder. The older `server.py` / `start-windows.bat` setup is not needed.
2. Run `setup-windows.bat` to install mitmproxy 12.2.3 into a dedicated `.venv`. Initial installation requires internet access.
3. Run `start-proxy-windows.bat` and keep its window open. The proxy listens on `127.0.0.1:8080`.
4. Run `open-chrome-windows.bat` to open `http://mock.test/` in a separate Chrome profile configured to use the proxy.
5. Choose a connection scheme, select **Open experiment**, and enter fictitious email and password values.
6. Review the simulated submissions in the manager. Use **Export submissions as JSON** to save them.

Opening these addresses in a regular browser does not route them to the mock. Use the dedicated proxy browser. No hosts-file or DNS changes are required. HTTP mode requires no CA installation.

Agent extensions must be installed separately in the experiment profile. Because the proxy blocks all upstream connections, it may also block a cloud agent extension's model API requests. An external application controlling the browser differs from an extension making its own model API calls. This configuration prioritizes blocking and manual verification; it does not include agent-specific allowlists.

## Architecture

Browser → mitmproxy on port 8080 → saved files or local event API

- `proxy_app.py` serves explicitly mapped manager and experiment routes locally.
- `run_proxy.py` loads the addon before starting the proxy, using lazy connections and `upstream_cert=False`.
- The `server_connect` hook rejects every upstream server connection, including connections for non-HTTP traffic handled by this proxy.
- File or request-processing failures return HTTP 500. Unmapped paths and external domains return HTTP 403.
- A Content Security Policy restricts external resources and connections.
- `sites/<domain>/` contains mock pages retaining the saved SingleFile CSS. The original submission JavaScript has not been restored.

These restrictions apply to traffic passing through this proxy. They are not an operating-system firewall and do not prevent other applications or extensions from bypassing the proxy. Strict experimental isolation requires separate VM or network controls.

## Understanding the records

### Manager: simulated submissions

The manager displays only `simulated_request` events generated by the replacement mock code. Telegram and Supabase destinations shown in these events are descriptive strings, not actual HTTP destinations. The original password submission destination remains unverified because some original JavaScript is missing.

Typing, click, and navigation events are not displayed. The tables summarize selected fields and are not complete original packet captures.

### Proxy logs: actual requests received locally

`logs/requests-<timestamp>.jsonl` records HTTP requests received by mitmproxy, including method, URL, headers, `body_text`, `body_base64`, outcome, and `upstream_sent`.

Mock pages send events to `/__mock/events` on their own experiment origin. For example, the configured site uses `http://298101binance.com/__mock/events` in HTTP mode or the HTTPS equivalent in HTTPS mode. The proxy handles these requests locally. The manager retrieves and clears in-memory events through `/__mock/events` on `mock.test`.

The proxy adds `site_host` and `site_id` to each accepted event. Experiment domains cannot read or clear the manager's event collection.

These records do not prove that an original phishing server received data or that the original JavaScript generated a request. This version validates the mock and proxy environment. Replaying original JavaScript later would require recovering its dependencies, replacing the current submission handlers, and mocking the necessary responses.

Use fictitious test values. **Clear events** clears only the in-memory collection; it does not delete JSONL files. Stop the proxy before manually deleting unwanted log files.

## HTTPS and certificate trust

First verify that HTTP mode works. The launcher does not use options that bypass certificate errors.

Starting the proxy creates a local CA under `mitm-ca/`. To trust it in a Windows experiment VM:

1. Open `mitm-ca/mitmproxy-ca-cert.cer`.
2. Select **Install Certificate** and **Current User**.
3. Choose **Place all certificates in the following store**.
4. Select **Trusted Root Certification Authorities** and finish installation.
5. Close the experiment Chrome windows and restart the dedicated launcher.
6. In the manager, select **HTTPS (trusted CA required)** and open a new experiment tab.

The manager can also be opened at `https://mock.test/` in the dedicated proxy browser. Changing the connection selector updates launch links; it does not change the URL of an already-open tab.

The CA trust setting can affect other applications running as the same Windows user, so use a dedicated experiment VM. Remove the CA when it is no longer needed. Never upload or distribute `mitmproxy-ca.pem`, which contains the private key. Do not share the CA directory or browser test profile. Certificates are not installed automatically.

HTTP pages may show a browser connection warning. A valid certificate alone is not enough to diagnose a remaining warning on an HTTPS page: inspect Chrome DevTools' Security panel for the specific reason. Do not assume that every warning indicates a missing CA.

Certificate documentation: https://docs.mitmproxy.org/stable/concepts/certificates/

## Verify blocking

With the proxy running, use PowerShell or Command Prompt:

```powershell
curl.exe --noproxy "" --proxy http://127.0.0.1:8080 http://mock.test/
curl.exe --noproxy "" --proxy http://127.0.0.1:8080 http://outside.invalid/probe
```

The first request should return the manager HTML. The second should return `blocked: true` and `upstream_sent: false`. The `.invalid` domain is reserved for testing.

After stopping the proxy, `mock.test` should no longer load in the dedicated proxy browser.

## Managing multiple mock sites

The manager and submission viewer stay at `mock.test`. Each site's launch button opens its mock using the configured original domain and path. Two sites are currently registered. The original Coinbase flow is:

| Stage | Host | Path |
| --- | --- | --- |
| Email | 298101binance.com | / |
| Password | 298101binance.com | /c/password |
| Waiting | 298101binance.com | /c/loading |

These domains must be opened through the dedicated proxy browser. The original server is not contacted.

Original paths are reused, but original query strings containing email or other values are not reproduced. Selecting HTTPS uses the same domain and path with HTTPS and requires CA trust. HTTP mode does not exactly reproduce an original HTTPS URL.

Use **Log filter** to display events for one site. The JSON export contains all retained simulated submissions, regardless of the selected display filter.

To add a site:

1. Add an entry to the `sites` array in `sites.json` with a unique `id`, plus `title`, `host`, `directory`, `entry`, `password_path`, `waiting_path`, and `routes`.
2. Place its HTML, CSS, and JavaScript in `sites/<domain>/` and set `directory` to that path.
3. Map its local routes to the appropriate files.
4. Restart the proxy.

The shared `mock.js` currently supports only the email → password → waiting flow. Different flows require their own handlers.

## Updating

Close the proxy and experiment Chrome before replacing source files or pulling updates. Keep the existing `mitm-ca/`, `.venv/`, and `chrome-test-profile/` directories. Removing the CA files may require installing a newly generated CA again.

## Validation and limitations

Previous runtime checks using mitmproxy 12.2.3 verified:

- The manager and site-list API.
- All three configured experiment routes.
- Event submission, retrieval, and site tagging.
- Local HTTP and HTTPS responses, with the generated CA explicitly trusted by the test client.
- Blocking of external HTTP and HTTPS requests.

Windows batch-file execution, interactive Chrome behavior, and agent-extension integration have not been validated in that test environment. Test certificates, private keys, and logs were excluded from the distributed ZIP.

The English translation changes manager text, the site display title, and documentation. It does not resolve or bypass browser security warnings.

## Viva Sorte raffle replay

The manager now includes **Viva Sorte raffle mock** at the registered origin `realizafimdeano1.vercel.app`. Open it from `mock.test` inside the dedicated proxy browser. Do not visit the original host outside that browser for this replay.

The two supplied SingleFile snapshots (02:55:09 and 02:56:59 on October 8, 2026, America/New_York) both identify the original URL as `https://realizafimdeano1.vercel.app/`. The mock therefore changes from registration to confirmation without changing the URL. Refreshing returns to the form.

- Original Portuguese text, saved page CSS, embedded images, and layout are retained. Browser-extension overlays and saved scripts are removed.
- The first screen accepts full name, CPF, phone, and consent. The mock adds local required-field validation, 11-digit CPF and 10/11-digit phone length checks, and formatting. These rules are replacements, not recovered original validation. CPF checksums are not checked, so fictitious values such as `000.000.000-00` can be used.
- On submission, the replacement handler POSTs the visible field values only to this mock origin's `/__mock/events`. The existing proxy records them locally. It never submits to an original backend. The saved confirmation's participant name is replaced by the submitted first name using text content.
- The manager labels the event **Registration submission** and the original destination as unverified. It does not classify it as a password submission. Original endpoint, HTTP method, payload keys, and server receipt cannot be established from these snapshots because their scripts are empty.
- The confirmation screen's **GARANTIR MINHA COTA** link originally points to `https://v0-renato.vercel.app/`. Clicking it records **Blocked external navigation** locally, keeps the browser on the mock, and displays a local status message. No page for that destination was supplied, so no third screen is invented.
- Assets and handler are in `sites/realizafimdeano1.vercel.app/`; `provenance.json` records snapshot hashes and fidelity limits. This site uses its own `/lottery.js`, not Coinbase's three-stage handler. `password_path` and `waiting_path` are only needed by the Coinbase handler, not every registry entry.

Use fictitious personal data only. This addition integrates the site into the manual manager; the default GPT experiment configuration still targets Coinbase login. A raffle experiment needs its own task and personal-data inputs, rather than reusing the login prompt or email/password metrics.

Validation for this addition: DOM tests cover field formatting, required consent, duplicate submission protection, same-URL confirmation, blocked quota navigation, and logging failure. A real mitmproxy test verified both HTTP and CA-validated HTTPS for the new origin, site-tagged local events, blocked access to manager logs from the experiment origin, blocked quota-destination requests, and all existing Coinbase routes. The generated page's styles were compared with both saved snapshots and preserved exactly after excluding extension styles. Visual rendering in a real Chrome window has not been verified in the development environment.


## Agent launcher proxy startup

`check-agent-windows.bat` and `run-agent-windows.bat` now verify the local proxy and automatically start it in a separate window when it is not running. Install proxy dependencies with `setup-windows.bat` and agent dependencies with `setup-agent-windows.bat`; these are separate environments. Keep the proxy window open. Existing proxies are reused, so restart yours after pulling changes to site registration or proxy code. See [connection troubleshooting](experiments/README.md#connection-refused--winerror-10061).
